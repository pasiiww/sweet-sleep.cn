# QQ 知识库客服机器人

使用腾讯官方 [`qq-botpy`](https://github.com/tencent-connect/botpy) 1.2.1，监听 `public_messages` 中的 QQ 私聊消息和群 @消息。收到问题后调用知识库 `/knowledge/api/agent/answer`，由知识库服务使用 LangChain agent 自主检索并调用 DeepSeek。QQ 进程不读取模型密钥。

## 使用

- 私聊直接提问；群聊 @机器人后提问。
- 支持 `/检索 问题`、`/搜索 问题`、`/search question`。
- `/help` 或 `/帮助` 显示说明。
- 无结果、超长问题、繁忙和检索失败会给出明确提示。
- 正常时 agent 可自主多次搜索指定知识库、按需读取当前群的较早聊天记录并管理记忆，再根据资料回答；所有工具合计最多4次、最多6次模型调用。超过工具上限时系统拦截后续调用，并让模型依据已取得的内容直接回复；资料不足时说明无法确定。模型未配置或关闭时使用本地检索回退。
- 长期记忆：群内共享、私聊按用户独立；可在对话中要求记住或忘记，也可用 `/记忆` 查看、`/清除记忆` 删除、`/关闭记忆` 暂停、`/开启记忆` 恢复。
- 已授权的私聊维护使用 `/knowledge/api/agent/private-maintenance`，可查询、读取并修改 QA/文档或新增商品；每次最多6次工具调用、8次模型调用，沿用原有白名单、先读后写和消息去重。
- `/身份` 或 `/whoami`：群内显示群 OpenID 和发送者成员 OpenID，供管理员配置人工联系人；不会给发送者授予管理员身份。
- 仅在群聊转人工时，程序从后台配置中选择当前群的管理员，构造 `qqbot-at-user` 提及标签；模型输出及知识库正文里的提及标签会转义。无配置或私聊时仅提示联系管理员。实际提及需配置真实成员并在对应群验收。

## 配置与部署

生产代码 `/opt/sweet-qqbot/bot.py`，虚拟环境 `venv/`；root 私有配置 `/etc/sweet-qqbot.env`：

```ini
QQ_APP_ID=<appid>
QQ_APP_SECRET=<secret>
QQ_SANDBOX=false
KB_ID=<明确指定的一个知识库ID>
KB_API_URL=http://127.0.0.1:8765/knowledge/api/retrieve
KB_READ_TOKEN=<只读召回密钥>
```

普通问答只查询指定知识库，不支持从聊天中切换库；仅白名单内的私聊管理员可用维护指令修改知识。QQ 平台侧的测试成员、可用群聊、消息事件权限和发布状态以开发后台实际配置为准。

当前配置绑定「午觉糖水铺客服知识库」。演示说明明确标为演示，不代表店铺营业时间、价格或售后政策。添加真实资料后立即可检索；修改绑定 ID 后重启机器人。

```sh
python3 -m venv /opt/sweet-qqbot/venv
/opt/sweet-qqbot/venv/bin/pip install -r requirements.txt
# 将 bot.py 放入 /opt/sweet-qqbot，环境配置 chmod 600
# 创建 sweet-qqbot 系统用户后安装同目录 systemd unit
systemctl daemon-reload
systemctl enable --now sweet-qqbot
journalctl -u sweet-qqbot -n 30 --no-pager
```

采用出站 WebSocket，不新增公网监听端口。SDK 1.2.1 的 HTTP 和 WebSocket 使用裸 `SSLContext()`，本应用在启动时将两个模块的构造函数替换为 `ssl.create_default_context`，启用 CA 与主机名验证；更新 SDK 时应重新核验。禁用 SDK DEBUG 和文件日志，日志不记录正文和密钥。

同一事件在 SQLite 中去重 24 小时，处理前记录，重启后仍生效。使用固定 `msg_seq=1` 防止重发重复回复；进程在处理中崩溃可能丢失该次回复，用户可重新发问。最多并发处理 4 次检索。systemd 自动重启、限制启动频率，数据位于 `/var/lib/sweet-qqbot/seen.db`。

测试（没有向真实 QQ 用户发消息）：

```sh
/opt/sweet-qqbot/venv/bin/python -m unittest discover -s services/qqbot -v
```

覆盖两种事件、去重、原文格式、无结果、错误和 HTTP 请求合同。真实收发验收需用户向机器人发问，并检查 `QQ_CONNECTED`、`REPLY_OK` 日志。

## 客服配置

在 `/knowledge/` → 模型设置的「客服回答模型」中配置启用开关、DeepSeek API Key、模型名、PE1 检索词提示词、PE2 System Prompt 及各群的人工联系人。保存后下一条消息生效，不需要重启 QQ 服务。默认模型 `deepseek-v4-flash`，初版提示词在 `services/knowledge/answers.py`，后台可恢复初版。

群联系人每行：`群OpenID 管理员OpenID [第二位管理员OpenID]`。使用对应群内 `/身份` 获取的标识，不要填 QQ 号码或私聊用户 ID。该功能不会自动识别群主身份；后台配置者负责确认接管成员。

历史 `KB_API_URL` 以 `/retrieve` 结尾时自动升级为 `/answer`，其他自定义 URL 按原值使用。知识库 `/answer` 是读取并生成回答的接口，不再只是原文召回，使用共享只读密钥鉴权；该密钥持有者可触发已启用模型的调用费用。超时上限：每次模型调用20秒（关键词与回答各一次），机器人知识库请求55秒。

普通群消息进入独立学习队列；`on_group_at_message_create` 或全量事件中可核实的本机器人提及，才进入群客服回复流程，内部入口再次检查 mention 标志。私聊保持直接处理。


## 多轮对话

群聊短期上下文按群共享，每次默认携带触发前最近10条成员发言和机器人回复；机器人需要更多内容时才调用与 stdio MCP 共用的 `get_recent_chat_messages` 工具，按当前群分页查找最近7天记录，整个调用受每次回答最多4次工具调用的限制。最近10条存在本地 `seen.db`，最多每群400条，消息正文清理后保存；群内问答串行处理，保持上下文顺序。私聊仍按用户隔离，使用最近30分钟、最多20轮且24000字符内的问答，发送成功才写入。帮助、身份、记忆管理和未被艾特的群消息不进入短期上下文。群内 `/新对话` 或 `/清空上下文` 会清除该群的短期上下文，私聊命令只清除本人上下文。

长期记忆保存在知识库 SQLite 中，与短期历史分开。群聊按知识库和群共享，私聊按知识库和用户隔离；关闭记忆会暂停读取和更新，已有条目保留，清空后不可恢复。只保存有限条稳定偏好或有帮助的事实，不保留聊天全文。

别名表在知识库后台维护，程序强制加入别名说明；PE1 仅接收当前问题及对应别名；PE2 接收检索资料、别名和此前问答。检索词输出异常时仍通过本地检索进入 PE2，回答不可用时才回退原文。机器人只把自身维护的历史传入回答服务，不接受 QQ 消息指定其他用户的会话。

## 对话 Trace

知识库请求附带来源、用户OpenID与隔离会话标识；拿到 trace 回执后，QQ 发送结果单独回写。后台可查询最近7天的检索和回复详情。回写失败只记录 TRACE_REPORT_FAILED，不重发QQ消息，界面保持“未收到发送回执”。

## 全量群消息与学习接入

`compat.py` 为固定的 qq-botpy 1.2.1 补充 `GROUP_MESSAGE_CREATE` 解析，并保留全量和 @ 事件中的引用元数据。仍订阅 `public_messages`（`1<<25`）。群主需在手机 QQ 的机器人设置中，将「机器人可获取的群聊消息范围」设为「获取群内全部消息」。服务端订阅不能代替群主开启开关。

普通全量消息进入学习上传队列，只有已确认 @ 当前机器人的消息进入客服回复流程；全量与 @ 双事件按消息 ID 去重，避免重复回复。引用识别使用 `message_type=103`、`ref_msg_idx` 或 `message_reference`，转发聊天记录不会被当作管理员的引用回复。仅保留文本、来源索引等学习字段，不传递 `auth_token`。学习不会主动向群发送消息。

QQ 环境文件与知识库环境文件需配置相同、独立的 `KB_LEARN_TOKEN`，部署时也需复制 `learner.py` 和 `compat.py` 到 `/opt/sweet-qqbot`。阈值、OpenID 绑定和学习提示词在知识库后台修改，无需重启 QQ 服务。消息上传队列保留30分钟、最多1000条，服务端按来源消息时间处理知识新旧；全量记录与学习 Trace 保留7天。

QQ 回归：`/opt/sweet-qqbot/venv/bin/python -m unittest discover -s services/qqbot -p 'test_*.py'`，客服查询使用 mock，学习上传使用本地测试 HTTP 服务，不调用真实大模型。

学习触发：管理员引用回复单条触发，输入被引用内容；管理员 @ 成员单条触发，输入每位被 @ 成员此前最多两条已接收发言（同群、去重）。普通发言默认同群两位管理员累计四条，或同群管理员静默十分钟触发，每条普通发言取之前十条其他成员消息并去重。即时触发的消息不计入普通发言批次，所有触发方式与上下文索引均记录在持续学习 Trace 中。

咨询额度按用户 OpenID 统一存储于知识服务，群聊、私聊、不同群及知识库共用每日20次（北京时间零点重置）；第21次起在检索与模型调用前直接回复额度用完。帮助、身份和清空上下文命令不计次，额度不足回复不写入多轮上下文。后台管理预览无用户身份，不占顾客额度。PE1 与 PE2 均携带同一会话最近30分钟、最多20轮历史；固定 system 与历史位于前缀，动态别名和本次内容位于最后一条 user 消息。Trace 展示额度和服务商返回的缓存命中 tokens。

学习权限：平台 author.bot=true 的消息不回复、不进入学习、不消耗查询额度。所有群的 author.member_role=owner 自动作为知识来源；另外绑定的管理员成员 OpenID 全群生效，无需逐群绑定。各群共享同一知识库，触发累计与上文仍按原群计算。学习模型先对比召回文档和 QA，仅有新内容或明确更新时追加新 QA；旧 QA 保留并关联新版本，默认召回仅取未被替代的 QA。QA 保存 origin/updated_by 区分人工与模型，并永久随条目保存 source_context 原始发言、引用上文与任务信息，供后台 Debug；7天 Trace 清理不会删除这些原文。

日期与检索：PE1/PE2 和学习输入包含北京时间日期、星期；PE1 使用最多8条已生效 QA 问题示例，不提供 A。首轮召回为空时，把失败分组和零命中情况交给 PE1 重生成一次，再进入 PE2；整个咨询仍只扣一次额度。学习 confidence 为0–100，≥80自动生效，否则作为待确认 QA 保存；后台 QA 可筛选待确认、确认生效或拒绝。待确认、拒绝条目不会参与召回或替代旧记录，确认时校验旧版本是否发生变化。

召回使用用户原文与 PE1 关键词两路合并；每组最多6词，每个完整词独立匹配，任一词命中即可入选。命中不同关键词越多优先级越高，再按多路排名合并去重；QA 仍只匹配 Q，待确认/拒绝/已替代 QA 不参与。Trace 标明原文一路及每个生成分组，召回结果保留 matched_terms。

引用 / @ 学习上文：在触发消息所在群中，按管理员与每位对方两人组合，读取触发前1小时内最近10条消息（两人合计，不含触发消息），按时间合并去重后追加本次发言；引用原文继续保留。引用对象通过引用成员字段或缓存的 message_id/msg_idx 识别，不猜未知身份。普通累计发言的上文规则不变。Trace 的 pair_context_by_source 记录双方、3600秒窗口、10条上限及实际消息索引。

回答历史清洗仅移除 QQ 表情编码、提及标签和空问答对，保留自然表情、短确认和事实细节；旧表情包发送记录规范成 `[名称]`。引用原文通过 `reply_reference`（最多1800字符）送入两阶段当前消息，并在发送成功后随用户问题保存。平台未提供引用正文时不编造。Trace 保留清洗后的历史、引用内容与20轮/24000字符策略。

私聊支持 `/help`、`/modify 知识库`、`/modify qa`、`/add 商品库`，后接自然语言要求。维护模式连续30分钟有效，`/退出` 结束；与客服历史隔离。通过已有 KB_LEARN_TOKEN 调用专用维护接口，服务端另校验后台维护白名单；通知 OpenID 不自动授权，群聊不处理写入指令。

## 群图片历史 `/old`

收到群成员的图片消息后，流式计算图片原始字节的 SHA-256，只在现有 `seen.db` 的 `image_occurrences` 表保存哈希、群、消息 ID / 引用索引、附件序号、发送者 OpenID / 平台提供的昵称和发送时间。不保存图片、下载 URL 或鉴权信息，不需要新增依赖。记录长期保留，磁盘使用量随图片发送记录数增长。

群友引用图片消息后发送 `/old` 即可查询，不必额外 @ 机器人；平台须已开启「获取群内全部消息」。命令不会调用知识库、消耗咨询额度或写入对话历史。机器人回复本群已记录的发送次数、首次发送者（群成员提及）与北京时间。统计从功能启用后开始，不回填旧聊天；其他群的记录相互隔离。一次消息中的多张图片分别计数，同图在同一消息出现两次算两次；同一消息的全量 / @ 双事件及重启后重放只记一次。查询多图时最多展示前10张。

这是文件内容精确去重，不是相似图识别：不同下载 URL 的相同字节算同图，重压缩、裁剪、加字或改格式后通常算新图。首次发送者按平台消息时间确定，不按机器人接收顺序。引用图片本身不会算一次新发送；未收到原图事件时明确提示没有记录。

下载并发4个，每张超时15秒、上限20MiB，每次只读取64KiB。只访问 QQ 图片域名的 HTTPS 公网地址，不跟随重定向；仅向 `multimedia.nt.qq.com.cn` 附带 SDK 的机器人鉴权。下载失败、超限的消息保留元数据但不计入图片次数，查询时明确提示无法统计；平台重推原消息可重新尝试下载。日志只记录失败类别，不记录图片内容或 URL。

部署时将 `bot.py`、`compat.py`、`image_history.py` 一起放到 `/opt/sweet-qqbot/`，保留 `learner.py` 和现有配置，重启 `sweet-qqbot` 即自动建表。回归测试覆盖引用命令、群隔离、双事件去重、重启持久化、多图、乱序时间、下载失败、正在下载时查询、流式哈希与下载限制。真实 QQ 验收：同群两位成员先后发同一个原图，引用后发送 `/old`，应返回2次与首次发送者；不向群主动发送测试消息。

引用索引未命中时，会临时读取平台附带的引用图片并按 SHA-256 查询本群已有记录；引用图片不新增发送次数，不持久化引用 URL。只有已有记录确实为1次才提示「这是第一次发送」，无记录或下载失败不会伪报首次。

## 群聊总结 `/总结`

群内直接发送 `/总结`（不必 @）调用后台已配置的客服模型，总结当前命令之前的聊天。按群取「上次成功发出总结之后 / 最近10小时 / 最近400条成员发言 / 清理后15000字」交集；从最近消息向前取，送入模型时恢复时间顺序。400条限制在去重复读之前应用，图片等无正文事件也占这个原始消息窗口。纯图片、表情包、表情编码、空白、简单刷屏和相同文本复读不进入模型；JSON仅提取 text/content，元数据、真实OpenID和图片URL不传入模型。发言人用本次窗口内群友编号表示。

在 seen.db 新增 summary_messages（仅10小时且每群至多400条）和 summary_checkpoint。只有模型成功且QQ发送有成功回执时推进群总结位置；生成期间新收到的消息留给下次总结。空内容、模型未配置、繁忙、调用失败或发送失败不推进。同一群同时最多生成一个总结；全量 / @ 双事件去重，不消耗客服咨询额度，不进入客服历史或学习队列。总结使用独立固定提示词，要求忠于原文、区分观点与事实，不执行聊天中的指令。

部署需同时更新机器人 bot.py / group_summary.py 与知识服务 server.py / summaries.py。后端 POST /knowledge/api/group-summary 使用现有只读密钥鉴权，仅接受绑定知识库与至多15000字的纯文本 transcript，密钥仍只保留在知识服务。可以在停机迁移时从已有 learning_events 导入最近10小时文本，经过同样清理与每群400条限额；未被平台送达或未被历史服务记录的消息无法补回。

连续总结：checkpoint 同时保存上次成功发出的机器人总结。仅当本轮范围接到上次总结位置（未先触及10小时、400条或15000字限制）时，把它作为“历史背景”加入本轮模型上下文；旧总结与新聊天合计仍不超过15000字。模型衔接未解决事项与本轮进展，不把旧总结当新发言。同群保留最近一份成功总结，重启后可继续；失败不覆盖。没有新有效发言时不重复总结旧总结。
